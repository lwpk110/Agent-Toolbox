# ADR-011：GitOps 同步推送到专用分支，不覆盖仓库基线锁文件

- **状态**：`Accepted`
- **日期**：2026-11-28
- **修订**：[ADR-006](./006-gitops-and-vault.md) 的推送目标与锁文件职责（不改变「配置与密钥解耦」）

## 背景与问题

[ADR-006](./006-gitops-and-vault.md) 决定用 GitHub 同步清单、锁文件、Skill 与知识原文，且密钥不进仓库。若运行时同步直接推 `main`，或用环境里生成的锁文件覆盖仓库根目录已跟踪的 `toolbox.lock.json`，会把本机临时指纹写进主干，也会让「git 跟踪的基线锁」和「某次运行时的锁」缠在一起。

根目录 `toolbox.lock.json` 是仓库基线（见 ADR-004）。运行时数据和测试必须使用独立的数据 / 锁文件路径。

## 备选方案对比

| 方案 | 优点 | 缺点 | 结论 |
| :--- | :--- | :--- | :--- |
| **方案 A**：同步直接推 `main`，并用运行时锁覆盖根目录锁文件 | 实现直接 | 主干历史被本机状态污染，基线锁失去审查意义 | 否决 |
| **方案 B**：不同步 lock，只同步 manifest | 避免覆盖基线 | 其它设备无法复现已审查的工具指纹 | 否决 |
| **方案 C（采用）**：同步推送到专用分支（默认 `toolbox-sync`），不推 `main`，也不覆盖仓库根目录的基线 `toolbox.lock.json` | 保留 GitOps 恢复能力，主干与基线锁仍受 PR 保护 | 需要约定同步分支与恢复流程 | **采纳** |

## 决策与工程后果

- 控制台 / CLI 的推送目标是专用分支（默认 `toolbox-sync`），不得直接更新 `main`。
- 同步中的 lock / manifest 不得写回覆盖仓库根目录已跟踪的基线 `toolbox.lock.json`。
- 推送仍遵守 ADR-006 的门禁：无明文密钥、Vault 完整、无未处理隔离项。
- 从同步分支恢复到本机时，只更新运行时数据文件；若要提升基线锁，必须走审查后的 PR。
